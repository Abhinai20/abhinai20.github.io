How JSON Schema describes data

A schema is itself JSON, describing the shape another document must have. The core keywords:

  • type — object, array, string, number, integer, boolean, null.
  • properties — the schema for each named field of an object.
  • required — an array of property names that must be present.
  • items — the schema every element of an array must satisfy.
  • enum — an explicit list of permitted values.
  • format — a semantic hint such as email, uri or date-time.
  • additionalProperties — whether fields not listed are allowed.

Gotchas worth knowing

Listing a property does not make it required

This catches nearly everyone once. properties only says "if this field appears, it must look like this" — an empty object validates against a schema with a dozen properties. Requiring a field means naming it in the separate required array, and forgetting that produces a schema that accepts almost anything.

additionalProperties defaults to true

Unknown fields are permitted unless you set it to false. That default is right for forward compatibility and wrong for catching typos: a config with reties: 3 instead of retries: 3 validates cleanly and then uses the default retry count. For configuration schemas, setting it to false turns a silent misconfiguration into an error at load time.

format is advisory in many validators

By specification, format is an annotation rather than an assertion, and several libraries do not enforce it unless explicitly configured to. A schema relying on "format": "email" for validation may be enforcing nothing at all. Where it matters, pair it with a pattern.

integer and number differ, and JSON has one numeric type

1.0 is usually accepted as an integer because it has no fractional part, while 1.5 is not. More awkwardly, large integers can lose precision passing through JavaScript, so an id beyond 2^53 may validate and still be wrong by the time it is used.

Draft versions are not compatible

Draft-04, Draft-07 and 2020-12 differ in real ways — exclusiveMinimum changed from a boolean to a number, and the keywords for array tuples were renamed. A schema written for one draft can be silently misinterpreted by a validator expecting another. Declare $schema explicitly and check what your library supports.

A generated schema is a starting point

Inferring a schema from a sample captures the shape of that sample, not your intent: optional fields that happened to be present become required, an enum is missed, and a nullable field looks non-nullable. Generation saves the typing; the constraints still need a human.
