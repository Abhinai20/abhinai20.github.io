Secret Scanner

Paste code, config, or logs and scan for accidentally-committed secrets (AWS keys, GitHub tokens, private key blocks, generic API keys, Slack tokens). Runs entirely in your browser — nothing is uploaded.

Paste some text and click "Scan".

What a leaked secret looks like

Scanners find credentials two ways. Some have recognisable shapes — AWS access keys start AKIA, GitHub tokens start ghp_, Slack tokens xox, private keys carry a -----BEGIN header. Everything else is caught by entropy: a long random-looking string assigned to a variable called token, secret or password is probably exactly that.

The usual places things leak are predictable: committed .env files, hardcoded fallbacks in config, connection strings with the password inline, test fixtures using real credentials, and CI definitions where someone pasted a value instead of referencing a secret store.

Gotchas worth knowing

Deleting the file does not fix the leak

This is the one that matters most. Once a credential has been pushed to a repository that others can read, it must be treated as compromised — removing it in a later commit changes nothing, because the old commit is still in the history, in every clone, and in any fork or cached view. Rotation is the fix. Revoke the credential and issue a new one; cleaning the repository is housekeeping done afterwards.

Rewriting history does not undo exposure either

Tools that purge a secret from every commit are useful for stopping future readers, but they cannot reach clones that already exist, forks, or anything that scraped the repository in the meantime. Automated scanners watch public pushes continuously and act within minutes. Assume anything public was collected.

Private repositories are not safe storage

A private repository can be made public by accident, shared with a contractor, backed up somewhere less controlled, or cloned onto a laptop that leaves the company. "Private" reduces who can read a credential today; it does not make the repository an appropriate place to keep one.

Scan before the commit, not after

A pre-commit hook that rejects a credential costs seconds; the same credential found after a push costs a rotation and an incident note. CI scanning is a useful backstop but it runs after the secret is already in the history.

False positives train people to ignore the tool

Example keys in documentation, test fixtures and high-entropy hashes all trip entropy rules. A scanner that cries wolf gets bypassed with --no-verify within a week, which is worse than not having it. Tune the rules and allowlist known-safe patterns deliberately.

The real fix is not having the secret there at all

Scanning is a safety net under a process problem. Credentials belong in a secret manager, injected at runtime, with short lifetimes and automatic rotation. Short-lived tokens issued through OIDC — so CI never holds a long-lived key at all — remove the entire category rather than detecting it.
