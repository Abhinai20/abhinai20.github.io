What a .env file is

A .env file is a list of KEY=value lines loaded into the environment at startup. It is the standard way to keep configuration out of code — and the format is less standardised than it looks.

  • One assignment per line, no spaces around =.
  • Keys conventionally uppercase with underscores.
  • # starts a comment.
  • Blank lines are ignored.

Gotchas worth knowing

There is no specification

Every loader implements its own dialect. Whether export prefixes are allowed, whether ${OTHER} is interpolated, how multi-line values and escapes work — all of it varies between the Python, Node, Ruby and Go implementations, and between Docker Compose and your application. A file that works locally can parse differently in the container, which is a genuinely confusing class of bug.

Docker Compose does not expand variables the way a shell does

An env_file is read literally: quotes become part of the value and $VAR is not interpolated. So PASSWORD="secret" yields a password including the quote marks. Compose also uses .env in the project directory for substitution in the compose file itself, which is a different mechanism from env_file — two things with the same name doing different jobs.

Spaces around the equals sign break it

KEY = value often produces a key with a trailing space, a value with a leading one, or nothing at all. Similarly, a trailing space after a value is invisible in an editor and included in the value — a frequent cause of a token that looks correct and is rejected.

Everything is a string

There are no types. DEBUG=false arrives as the string "false", which is truthy in most languages. Parsing booleans and numbers explicitly, rather than relying on the value looking right, avoids a whole family of config bugs.

Precedence surprises people

Most loaders do not overwrite a variable already present in the real environment, so a stale shell export silently wins over the file you just edited. When a change to .env appears to have no effect, check whether the variable is already set in the environment.

Never commit it

A .env file holding real credentials in a repository is one of the most common leak sources there is. Add it to .gitignore on day one and commit a .env.example with the keys and dummy values instead — that documents what is required without publishing anything, and gives new developers a working template.
