CIDR Overlap Checker

Paste two CIDR blocks (one per line, or more) and check whether any of them overlap — useful for VPC/subnet planning.

Paste CIDR blocks and click "Check Overlaps".

What counts as an overlap

Two CIDR blocks overlap when any address belongs to both. In practice that takes one of two forms:

  • Containment — one range sits entirely inside the other, as 10.0.5.0/24 does inside 10.0.0.0/16.
  • Identical — the same range allocated twice in different places.

Properly aligned CIDR blocks cannot partially overlap: because every block starts on a boundary that is a power of two, two ranges are either disjoint or one contains the other. A partial overlap means one of the inputs is not a valid network address.

Why overlaps matter

Peering and VPN are refused outright

Overlapping ranges cannot be peered — the request fails rather than degrading, because the routing would be ambiguous. The same applies to site-to-site VPN and Direct Connect back to a corporate network. This is usually discovered at exactly the wrong moment: when two environments that were built independently need to talk.

Routing becomes ambiguous

Where overlapping routes do coexist, the most specific prefix wins — a /24 route beats a /16 covering the same addresses. That makes behaviour depend on which routes happen to be installed, which is a very difficult class of bug: traffic to one host works and another does not, with nothing obviously wrong at either end.

Security group references stop being meaningful

Rules written against CIDR ranges rather than security group IDs silently widen when ranges overlap, because a rule intended for one environment also matches addresses in another.

Gotchas worth knowing

The default ranges collide constantly

Almost every tutorial and default template uses 10.0.0.0/16 or 172.17.0.0/16, so independently built environments collide the first time anyone tries to connect them. Docker's default bridge is 172.17.0.0/16, which also conflicts with the lower end of the private 172.16.0.0/12 range used by some corporate networks — a classic cause of a container losing access to an internal service.

Check against everything, not just cloud

The comparison set has to include on-premises networks, VPN client pools, partner networks you might peer with, and Kubernetes pod and service CIDRs — which are separate ranges that must not collide with the VPC or with each other.

Renumbering later is the expensive option

Changing a subnet's range means recreating it and everything in it. Keeping a simple allocation registry, even a spreadsheet, costs a few minutes per environment and avoids that entirely.
