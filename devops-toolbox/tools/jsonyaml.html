How the two formats relate

YAML 1.2 is a superset of JSON, which means any valid JSON document is already valid YAML and converting one way is lossless. Going the other direction is not always, because YAML has features JSON has no way to express: comments, anchors and aliases, multiple documents in one file, and several scalar styles.

In practice the conversion people want is "make this configuration readable" or "feed this config to a tool that only speaks JSON", and both work fine as long as you know what YAML is doing with your unquoted values.

Gotchas worth knowing

The Norway problem

Under YAML 1.1 rules, which many parsers still follow, the unquoted scalars y, n, yes, no, on and off are booleans. A country list containing NO for Norway yields false. The same rule turns a config value of on into true. Quote any string that could be mistaken for a boolean, and be deliberate about it in generated files.

Version numbers lose their meaning

version: 1.10 parses as the float 1.10, which is 1.1, so the patch digit vanishes. version: 1.2.3 stays a string because it is not a valid number, meaning the type of the field changes depending on the value — a trap in anything that compares versions. Quote version strings always.

The same applies to anything with leading zeros: an identifier like 012345 may be read as octal or silently stripped to 12345, which breaks zip codes, account numbers and ids.

Tabs are forbidden

YAML indentation must be spaces. A single tab character produces a parse error that often points at a confusing line, and editors configured to insert tabs will reintroduce it every time. Setting the editor to expand tabs for .yaml files saves repeated frustration.

Indentation is the structure

Unlike JSON's braces, nesting in YAML is carried entirely by leading whitespace, so a block pasted at the wrong depth is still valid YAML — just describing something different. This is the most common cause of a Kubernetes manifest applying cleanly and doing the wrong thing, because the field landed on the wrong parent.

Comments and anchors do not survive the round trip

JSON has no comment syntax, so converting YAML to JSON and back loses every comment and expands every alias. If the YAML file is maintained by people, convert for consumption rather than editing the JSON and converting back.

Multi-document files

YAML allows several documents in one file separated by ---, which Kubernetes manifests use constantly. JSON has no equivalent, so such a file converts to an array of objects or has to be split. A converter handed a multi-document file that returns only the first document has silently dropped the rest.
