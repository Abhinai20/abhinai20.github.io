Verifying when a schedule will actually fire

Calculating the next few run times is the fastest way to check an expression means what you think. It catches the mistakes reading the syntax does not — a schedule that is an order of magnitude more frequent than intended, or one that will not fire for another eleven months.

Two patterns are worth testing every time: the gap between consecutive runs, and the first run after a month or year boundary.

Gotchas worth knowing

A missing field makes it far more frequent

The classic error is writing 0 2 * * meaning "2am daily" and getting four fields instead of five. Depending on the parser, that is either an error or a schedule that runs every hour. The inverse is just as common: * 2 * * * runs sixty times between 02:00 and 02:59, not once at 2am.

Day-of-month and day-of-week combine as OR

When both are restricted, the job runs when either matches — so 0 0 1 * 1 fires on the 1st of every month and every Monday, which is far more often than "the first Monday". Listing the next ten runs makes this immediately obvious, which is exactly why it is worth checking rather than reasoning about.

Short months and the 31st

0 0 31 * * simply does not run in months without a 31st, so a monthly job skips February, April, June, September and November. "Last day of the month" has no standard cron expression; the usual approach is to run on the 1st and process the previous month, or to check the date inside the job.

Daylight saving shifts or duplicates a run

A job scheduled inside the hour that is skipped when clocks move forward does not run that day. In the repeated hour when they move back, it can run twice. Some implementations compensate and others do not, so the only reliable answers are to schedule in UTC or to make the job idempotent.

The next run is not the next start you will see

Calculated times assume the scheduler fires precisely. In practice a busy host, a container still pulling an image, or a hosted scheduler under load can delay a run by minutes — and hosted cron services explicitly offer no exact-time guarantee. If a run being late by ten minutes breaks something, the schedule is not the right mechanism.

Catch-up behaviour varies

If the machine was off at the scheduled time, plain cron does nothing — the run is simply lost. anacron and systemd timers with Persistent=true will run the job once the system is back. Kubernetes CronJobs behave differently again, with startingDeadlineSeconds deciding whether a missed run is attempted. Knowing which you are using determines whether "it did not run" is a bug or the documented behaviour.
