VPC Subnet Planner

Split a VPC CIDR into evenly sized per-AZ subnets. Shows each range and the real usable host count — AWS and Azure both take five addresses out of every subnet, which is the part that catches people out.

Enter a CIDR and click "Plan subnets".

Planning VPC address space

Subnet layout is one of the few cloud decisions that is genuinely hard to change later, so it is worth spending time on before the first resource is created.

The usual shape is a VPC CIDR divided per availability zone, and within each zone a public subnet for load balancers and NAT, and a private subnet for compute and databases. Three availability zones is the common baseline, which means at least six subnets.

A workable default

A /16 VPC split into /20 subnets gives sixteen blocks of roughly 4,000 addresses — enough for three zones of public and private subnets with plenty spare for later tiers. Generous sizing costs nothing: unused private address space is free.

Gotchas worth knowing

AWS reserves five addresses per subnet

Not two. The network address, the broadcast address, and the first three usable addresses are taken by the VPC router, DNS, and a reserved slot. A /28 therefore yields 11 usable addresses rather than 14, which is exactly the size where it hurts.

A VPC CIDR cannot be shrunk

You can add secondary CIDR blocks to an AWS VPC, but you cannot resize or remove the primary one, and a subnet's range is fixed for its lifetime. Undersizing means migrating workloads into new subnets later — which touches security groups, route tables and anything with a hardcoded address.

Overlapping ranges block peering forever

Two VPCs with overlapping CIDRs cannot be peered, and the same applies to a VPN or Direct Connect back to on-premises. Using 10.0.0.0/16 because it is the default is how two environments end up unable to talk to each other. Allocate from a registry of ranges across the whole organisation, including the corporate network, before creating anything.

Kubernetes needs far more addresses than you expect

With the AWS VPC CNI, every pod takes a real subnet IP, and each node pre-allocates a block of them. A cluster of modest size can exhaust a /24 quickly, and IP exhaustion presents as pods stuck in ContainerCreating rather than as a networking error. Size node subnets for pods, not for nodes.

One NAT gateway per zone, or none

Routing all private subnets through a single NAT gateway saves money and creates both a single point of failure and cross-zone data charges. One per availability zone is the resilient pattern; be deliberate about which you are choosing rather than inheriting it from a template.

Leave gaps between allocations

Allocating contiguously means the next subnet has nowhere to grow. Leaving a block spare after each tier costs nothing in a private range and makes later expansion a change rather than a migration.
