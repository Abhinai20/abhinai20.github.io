The objects a service needs

Running something on Kubernetes usually means three objects working together, each with a distinct job:

  • Deployment — declares the pod template and how many replicas, and manages rollouts.
  • Service — gives those pods a stable name and virtual IP, selecting them by label.
  • Ingress — routes external HTTP traffic to a Service by host and path.

ConfigMaps and Secrets supply configuration, mounted as files or injected as environment variables.

Gotchas worth knowing

Labels are the wiring, and they must match exactly

A Service finds pods through spec.selector matching the pod template's labels — not the Deployment's own labels, which is the distinction people miss. One typo and the Service has no endpoints, presenting as connection refused rather than as a configuration error. kubectl get endpoints <service> showing none is the fastest confirmation.

targetPort and port are different things

port is what the Service listens on; targetPort is the container's port. Setting them to the same value out of habit works until they differ, and then traffic goes nowhere. Naming the container port and referring to it by name in the Service is more robust than repeating a number in two places.

ConfigMap changes do not restart pods

Updating a ConfigMap does not roll the Deployment. Values mounted as volumes update in place after a delay, but anything read at startup — and every environment variable — keeps the old value until the pod restarts. The common fix is to put a hash of the config in a pod annotation so that changing it naturally triggers a rollout.

Secrets are base64, not encryption

A Secret is encoded, not encrypted, and anyone who can read the object can read its contents. Committing one to git publishes the credential as surely as committing the plaintext would. Encryption at rest must be enabled on the cluster, and access controlled through RBAC, before a Secret is meaningfully secret.

Namespace is easy to forget

A manifest without an explicit namespace lands wherever the current context points, which is how objects end up in default and then cannot find each other. Cross-namespace DNS needs the fully qualified form, service.namespace.svc.cluster.local — the short name only resolves within the same namespace.

Generated manifests need review, not just application

A generator gives you a correct skeleton, not a production-ready object. Resource requests, probes, security context, replica count and disruption budgets all depend on what the workload actually does, and none can be inferred from an image name. Treat generated YAML as a first draft.
