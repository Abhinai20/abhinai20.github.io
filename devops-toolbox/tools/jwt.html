What a JWT actually contains

A JSON Web Token is three base64url-encoded segments joined by dots: header.payload.signature. The header says which algorithm signed it, the payload carries the claims, and the signature is what makes the first two trustworthy.

The important consequence of that structure: the payload is encoded, not encrypted. Anyone holding the token can read every claim in it without any key at all — which is exactly what this decoder does, entirely in your browser.

Standard claims

  • iss — issuer, who minted the token.
  • sub — subject, usually the user id.
  • aud — audience, who the token is intended for.
  • exp — expiry, as a Unix timestamp in seconds.
  • nbf — not valid before this time.
  • iat — when it was issued.
  • jti — a unique id, used to revoke or de-duplicate.

Gotchas worth knowing

Decoding is not verifying

This is the mistake that matters. Reading the claims out of a token tells you what it says, not whether it is genuine. Anyone can craft a token with "admin": true in the payload. Only checking the signature against the issuer's key proves the token was issued by whom it claims and has not been altered since. Never make an authorisation decision from a decoded payload alone.

alg: none and algorithm confusion

The header is attacker-controlled, so a library that trusts it can be told how to verify. Two classic attacks follow: setting alg to none so verification is skipped entirely, and switching an RS256 token to HS256 so the library uses the public key as an HMAC secret — a key the attacker already has. Pin the expected algorithm in your verification code rather than reading it from the token.

Put nothing secret in the payload

Because it is readable by anyone who holds the token, the payload is the wrong place for anything sensitive — no personal data beyond what is necessary, no internal identifiers you would not publish, and certainly no credentials. A token often ends up in browser storage, server logs and error reports.

Expiry is in seconds, and clocks drift

exp, nbf and iat are Unix timestamps in seconds, while many languages produce milliseconds by default. A token minted with a millisecond value will appear to expire tens of thousands of years from now. Verification should also allow a small clock-skew tolerance between the issuing and validating machines.

Revocation is the hard part

A signed token stays valid until it expires — there is no built-in way to withdraw one, because verification is deliberately offline. If you need to be able to log someone out immediately, you need short expiry times plus refresh tokens, or a server-side denylist keyed on jti. Choosing long-lived tokens because it is convenient is choosing not to be able to revoke access.

base64url is not base64

JWT segments use the URL-safe alphabet: - and _ instead of + and /, and the trailing = padding is stripped. A plain base64 decoder will often fail or produce garbage on a token, which is a common source of confusion when decoding one by hand.
