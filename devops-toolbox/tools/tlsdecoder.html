What is inside a certificate

An X.509 certificate binds a public key to one or more names, signed by a certificate authority. The fields that matter day to day:

  • Subject — who the certificate is for. The CN within it is the legacy name field.
  • Subject Alternative Name — the list of hostnames the certificate is actually valid for.
  • Issuer — which CA signed it. For a chain to validate, this must match the subject of the next certificate up.
  • Not Before / Not After — the validity window.
  • Key Usage / Extended Key Usage — what the certificate may be used for, such as server authentication.
  • Serial number and fingerprint — identifiers for pinning and revocation.

Gotchas worth knowing

CN is ignored by modern clients

Browsers stopped honouring Common Name for hostname matching years ago; only the Subject Alternative Name list counts. A certificate whose CN is right but whose SAN omits the hostname will fail validation with an error that looks nonsensical if you are reading the CN. Check the SAN first, always.

A missing intermediate is the classic failure

A server must send its own certificate and any intermediates, in order, so the client can build a path to a trusted root. Omitting the intermediate frequently still works in a browser, because browsers cache intermediates from previous sites — and then fails in curl, in a JVM, or on a mobile device that has no such cache. "It works in Chrome but not from the server" is nearly always this.

Chain order matters

The leaf certificate comes first, then each issuer in turn, and the root is optional because the client already has it. A bundle assembled in the wrong order is rejected by stricter stacks even though every certificate in it is valid.

Wildcards cover exactly one label

*.example.com matches api.example.com but not a.b.example.com, and not the bare example.com either. A wildcard certificate that needs to serve the apex domain must list it separately in the SAN.

Expiry is the outage you can predict

Certificates are the rare failure with a known date, and they still cause outages because nobody is watching the one on an internal load balancer or a message broker. Monitor expiry as a metric with alerting weeks ahead, rather than relying on a renewal reminder reaching a person who still works there. Automated renewal is better again — but then monitor that the renewal actually happened.

The clock is part of validation

A device whose time is wrong will reject perfectly good certificates as not-yet-valid or expired. On embedded hardware and freshly imaged machines without NTP, this presents as an inexplicable TLS failure that resolves itself once the clock syncs.

PEM and DER are the same data

PEM is base64 with -----BEGIN CERTIFICATE----- markers; DER is the raw binary. Tools disagree about which they accept, and a .crt file may be either. Converting between them changes nothing about the certificate itself.
