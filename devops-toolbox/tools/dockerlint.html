What makes a Dockerfile good

Most Dockerfile problems come down to three things: how big the image ends up, how often the cache is invalidated, and what the container runs as. The rest is detail.

Order instructions by how often they change

Each instruction produces a layer, and changing one invalidates every layer after it. Copying your whole source tree before installing dependencies means every code edit reinstalls everything. Copy the manifest first, install, then copy the source:

COPY package*.json ./ → RUN npm ci → COPY . .

That single reordering is usually the largest build-time win available.

Use multi-stage builds

Compilers, headers and build tools do not belong in a runtime image. Build in one stage, copy only the resulting artefact into a slim final stage, and the image shrinks by hundreds of megabytes while losing a large amount of attack surface with it.

Gotchas worth knowing

Cleaning up in a later layer saves nothing

Deleting a file in a subsequent RUN does not reclaim the space — the earlier layer still contains it, and the image carries both. The cleanup has to happen in the same instruction that created the files: RUN apt-get update && apt-get install -y --no-install-recommends foo && rm -rf /var/lib/apt/lists/*. The same applies to secrets: a credential added in one layer and deleted in the next is still in the image for anyone who pulls it.

:latest is not a version

It is just the default tag, and it moves. A build that worked yesterday can produce a different base image today, which turns a reproducible build into a lottery and makes rollbacks meaningless. Pin a specific tag, and pin by digest where the stakes justify it.

Containers run as root unless you say otherwise

Without a USER instruction the process runs as root inside the container, so a compromise starts with full privileges and a path toward the host via any misconfiguration. Create an unprivileged user and switch to it after installation, remembering that file ownership on anything copied in needs to match.

ADD does more than you want

It auto-extracts archives and can fetch remote URLs, both of which are surprising when you only meant to copy a file. Use COPY unless you specifically want extraction.

A missing .dockerignore sends everything

Without one, COPY . . ships .git, node_modules, local env files and build output into the image and the build context. That bloats the image, slows every build, and is a routine way credentials end up published. Treat it as mandatory, not optional.

ENTRYPOINT and CMD in shell form break signals

Written as a bare string, the command runs under /bin/sh -c, which does not forward SIGTERM to your process — so the container ignores a graceful stop and gets killed after the timeout. Use the exec form, CMD ["node", "server.js"], so your process is PID 1 and receives signals directly.
