Convert Kubernetes resource quantities (like 500m, 1Gi, 250Mi) into human-readable values.

Enter a quantity and click "Convert".

How Kubernetes expresses quantities

Kubernetes uses two different suffix families, and confusing them is the most common sizing mistake.

  • Binary: Ki, Mi, Gi, Ti — powers of 1024. 1Gi is 1,073,741,824 bytes.
  • Decimal: K, M, G, T — powers of 1000. 1G is 1,000,000,000 bytes.

The gap is about 7% at gigabyte scale and widens as the unit grows. For memory you almost always want the binary form, because that is how the kernel and the container runtime actually account for it.

CPU is measured in millicores

CPU quantities use m for thousandths of a core: 500m is half a core, 1000m is exactly one core, and a bare 1 means the same as 1000m. CPU is compressible — a container over its limit is throttled, not killed.

Gotchas worth knowing

1M is not one mebibyte

Writing memory: 512M when you meant 512Mi gives you about 24 MiB less than intended. That is usually harmless, until it is the margin that causes an OOMKill under load. The lowercase m is worse: memory: 100m is not 100 megabytes, it is 0.1 bytes, because m means milli. Kubernetes accepts it without complaint.

Memory limits are enforced by killing

Unlike CPU, memory is incompressible. A container that exceeds its memory limit is terminated with OOMKilled — there is no throttling, no warning, and the process gets no chance to shed load. The exit code is 137. Setting a limit lower than genuine peak usage converts a slow-memory problem into a crash loop.

Requests schedule, limits constrain

The request is what the scheduler uses to decide whether a node has room; the limit is what the runtime enforces at execution. Setting a request far below the limit lets the scheduler overcommit a node, which works until several pods peak together and the node starts evicting. Setting them equal gives the pod Guaranteed quality of service and the most predictable behaviour.

Node capacity is not what you can use

A node advertises capacity, but the kubelet reserves part of it for the system and the kubelet itself, leaving a smaller allocatable figure. Sizing pods against the node's total memory rather than its allocatable memory is why a pod that "obviously fits" stays Pending.

Fractional CPU below 100m behaves poorly

CPU requests translate to cgroup shares, and very small values give a container so little guaranteed time that it is starved under contention — which looks like random latency rather than a resource problem. If a workload is latency sensitive, do not request less than about 100m.
