How Unix permissions work

Every file and directory carries three permission sets: one for the owning user, one for the owning group, and one for everyone else. Each set has three bits — read, write and execute — which is why permissions are usually written as three octal digits.

  • 4 — read (r)
  • 2 — write (w)
  • 1 — execute (x)

Add them together per triad. 7 is read, write and execute; 6 is read and write; 5 is read and execute. So 755 means the owner can do everything while group and others can read and execute, and 644 means the owner can read and write while everyone else can only read.

The common values

  • 644 — ordinary files: owner edits, everyone reads.
  • 755 — directories, and scripts meant to be run by anyone.
  • 600 — private files such as credentials. SSH requires this for private keys.
  • 700 — a private directory only the owner may enter.
  • 775 — a shared directory for a team, writable by the group.

Gotchas worth knowing

On a directory, execute means "enter", not "run"

The x bit on a directory controls whether you may traverse into it and reach what is inside. Read without execute lets you list the names in a directory but not open anything within it; execute without read lets you open a file whose exact path you already know, but not list the contents. This is why 755 is normal for a directory even though nothing in it is a program.

chmod -R 755 makes every file executable

Recursive chmod applies the same mode to directories and regular files alike, so a whole tree of documents ends up marked executable. The usual fix is to treat the two separately:

find . -type d -exec chmod 755 {} + and find . -type f -exec chmod 644 {} +

Alternatively, symbolic mode with a capital X — chmod -R a+rX . — sets execute only on directories and on files that already had it.

umask subtracts, it does not set

New files are not created with the mode you might expect; the umask masks bits out of the system default. With the common umask of 022, a new file lands at 644 and a new directory at 755. If files are appearing with unexpectedly open or closed permissions, the umask of the creating process is usually the reason rather than anything chmod did.

The special bits

A fourth leading digit sets setuid (4), setgid (2) and the sticky bit (1). Setgid on a directory is the genuinely useful one: new files inside inherit the directory's group, which is what makes shared team directories work. The sticky bit is why /tmp is world-writable yet users cannot delete each other's files. Setuid on an executable runs it as the file's owner and deserves real caution.

Permissions are not ownership

chmod changes what the owner, group and others may do; it never changes who the owner or group is. If the right answer is "this should belong to a different user", that is chown. Granting 777 to work around an ownership problem is the reflex worth resisting — it makes the file writable by every account on the system, including any service that gets compromised.
