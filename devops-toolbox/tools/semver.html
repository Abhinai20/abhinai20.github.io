Version Constraint Checker

Check which versions actually satisfy a constraint. Handles npm semver (^, ~, ranges) and Terraform’s pessimistic ~>, which is not the same as npm’s tilde — ~> 1.5 allows 1.6 but ~> 1.5.0 does not.

Enter a constraint and click "Check".

How semantic versioning works

A semver version is MAJOR.MINOR.PATCH, and each part has a defined meaning: increment MAJOR for a breaking change, MINOR for backwards-compatible features, PATCH for backwards-compatible fixes. The value of the scheme is entirely in that promise — it lets a dependency manager decide what is safe to upgrade automatically.

Constraint operators

  • 1.2.3 — exactly this version.
  • ^1.2.3 — compatible with 1.2.3: allows MINOR and PATCH, so up to but excluding 2.0.0.
  • ~1.2.3 — allows PATCH only, so up to but excluding 1.3.0.
  • >=1.2.3 <2.0.0 — the explicit form of a caret range.
  • * or latest — anything, which is rarely what you want in a lockfile-less project.

Gotchas worth knowing

Caret behaves differently below 1.0.0

This surprises nearly everyone. For ^1.2.3 the caret allows minor upgrades, but for ^0.2.3 it allows only patch upgrades — up to but excluding 0.3.0. The reasoning is that pre-1.0 projects signal breaking changes with the minor number, and the rule bakes that convention in. So the same operator is permissive on a stable package and strict on an unstable one.

Pre-release versions sort below the release

1.0.0-alpha is older than 1.0.0, not newer, and pre-release identifiers compare field by field: 1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-beta < 1.0.0-rc.1 < 1.0.0. Numeric identifiers compare numerically, so alpha.2 precedes alpha.10 — unlike plain string sorting, which gets that backwards.

Ranges do not match pre-releases by default

^1.2.3 will not install 2.0.0-beta.1, and usually will not pick up 1.3.0-rc.1 either, because a range only considers pre-releases when the constraint itself names one. This is deliberate and usually right, but it means "why isn't it upgrading?" often has the answer "because the only newer version is a pre-release".

Build metadata is ignored in comparisons

Anything after a +, such as 1.0.0+build.42, has no effect on precedence — two versions differing only in build metadata are the same version as far as ordering is concerned. Using it to distinguish releases does not work.

The promise is a convention, not a guarantee

Nothing enforces that a minor release is actually backwards compatible, and plenty of breakage arrives in patch versions. This is why lockfiles exist: the range expresses intent, the lockfile pins reality. A project with permissive ranges and no committed lockfile is one upstream mistake away from an unreproducible build.

Leading v is not part of the version

v1.2.3 is a common tag style, but the version itself is 1.2.3. Some parsers strip it and some reject it, so comparing a git tag against a manifest version without normalising first is a reliable source of off-by-one-character bugs.
