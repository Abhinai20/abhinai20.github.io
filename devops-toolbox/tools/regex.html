Regex syntax reference

A regular expression describes a pattern to match inside text. These are the pieces you reach for most often.

  • . — any character except a newline.
  • \d \w \s — a digit, a word character, whitespace. Capitalised (\D \W \S) means the opposite.
  • [abc] — any one of these; [^abc] — any one except these; [a-z] — a range.
  • * + ? — zero or more, one or more, zero or one.
  • {2,5} — between two and five repetitions.
  • ^ $ — start and end of the string, or of a line with the multiline flag.
  • \b — a word boundary, which is what makes \bcat\b skip "concatenate".
  • (...) — a capturing group; (?:...) groups without capturing.
  • | — alternation, matching either side.

Flags

i ignores case, g finds every match rather than the first, m makes ^ and $ match at line boundaries, and s lets . match newlines too.

Gotchas worth knowing

Quantifiers are greedy by default

Given <b>one</b> and <b>two</b>, the pattern <b>.*</b> matches the entire string, not the first tag pair — .* takes as much as it can and then backs off only enough to let the rest match. Adding ? makes it lazy: <b>.*?</b> stops at the first closing tag.

Catastrophic backtracking is a real outage

Nested quantifiers over overlapping character sets, such as (a+)+b, can make the engine try an exponential number of paths before giving up. On a long non-matching input that is seconds or minutes of pinned CPU, and if the pattern runs on user input it is a denial-of-service vector with its own name, ReDoS. Prefer specific character classes over .*, avoid a quantifier inside a quantified group, and apply a timeout where the platform offers one.

. does not match newlines

By default a dot stops at a line break, so a pattern that works on single-line test input quietly fails on a multi-line document. The s flag (sometimes called "dotall") changes it. Note that m is a different flag doing a different job — it affects anchors, not the dot.

Escaping happens twice in most languages

A regex that works in a tester often breaks when pasted into code, because the string literal consumes one level of backslashes first. \d in a Java or JSON string has to be written \\d. Python raw strings (r"\d") and JavaScript regex literals (/\d/) avoid this entirely, which is why they are worth using.

Dialects genuinely differ

Lookbehind is unsupported in some engines and fixed-width-only in others. POSIX tools are a bigger jump: basic grep and sed need backslashes before +, ? and (, which is why grep -E exists. A pattern verified in a browser tester is verified for that engine, not universally.

Do not parse HTML with it

Regular expressions cannot describe arbitrarily nested structures, so a pattern over HTML, XML or JSON works on your sample and fails on real input containing a nested tag, an attribute with a bracket in it, or a comment. Extracting one simple value from predictable markup is fine; anything structural wants a parser.
