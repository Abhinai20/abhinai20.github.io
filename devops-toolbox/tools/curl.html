The flags you actually use

  • -X POST — set the HTTP method.
  • -H 'Header: value' — add a request header; repeatable.
  • -d '{"k":"v"}' — send a request body. Implies POST.
  • -o file — write the body to a file; -O keeps the remote filename.
  • -L — follow redirects.
  • -u user:pass — HTTP basic auth.
  • -i — include response headers in the output; -I sends HEAD and shows headers only.
  • -s — silent, suppressing the progress meter; usually paired as -sS so errors still show.
  • -w '%{http_code}' — print selected response metadata after the transfer.

Gotchas worth knowing

-X POST with -d is redundant, and sometimes harmful

-d already switches the method to POST. Forcing -X as well matters when a redirect is involved: curl normally changes the method to GET on a 301 or 302, but an explicit -X pins it, so the redirected request keeps POSTing to the new location. Omit -X unless you specifically need a method curl would not choose.

-d sets the wrong Content-Type for JSON

It defaults to application/x-www-form-urlencoded, so an API expecting JSON may reject a body that looks perfectly valid. Always pair it: -H 'Content-Type: application/json'. Newer curl versions offer --json as shorthand for the body, the content type and the accept header together.

-k disables certificate verification entirely

It is the standard reflex when a TLS error appears, and it turns off the protection that error exists to provide — including against interception. For a self-signed or internal CA, pass the CA bundle with --cacert instead. Reaching for -k in a script that handles anything sensitive is worth treating as a bug, not a workaround.

Quoting bites on Windows

A curl command copied from documentation usually uses single quotes, which cmd.exe does not treat as quotes at all. On Windows, use double quotes and escape the inner ones, or run the command in PowerShell with care — PowerShell also has its own parsing of -d and JSON braces. Pasting a Linux curl line into a Windows prompt unchanged is the most common reason it "doesn't work".

-d strips newlines, --data-binary does not

-d is line-oriented and removes newlines from a file passed with -d @file, which corrupts anything whitespace-sensitive — YAML, a binary payload, a signed blob. Use --data-binary @file when the body must arrive byte for byte.

curl does not fail on HTTP errors by default

A 500 response is still a successful transfer as far as the exit code is concerned, so a script checking only $? will sail past server errors. -f makes curl return a non-zero exit code on HTTP failures, which is what you usually want in automation.
